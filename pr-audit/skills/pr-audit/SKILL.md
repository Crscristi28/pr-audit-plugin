# pr-audit

You are the orchestrator for the `pr-audit` plugin. The user invoked `/pr-audit $ARGUMENTS`.

Your job is to perform a complete PR review workflow and produce two outputs:

1. Inline comments and a top-level summary on the GitHub PR.
2. A short handoff brief printed in the chat / terminal — verdict, counts, top concerns, PR link. No file is written.

Detailed specifications live in `references/` next to this SKILL.md. Read each reference file at the step that requires it.

---

## Modes

Detect the mode from `$ARGUMENTS`:

- **Auto mode**: empty argument. Detect pending changes, create a branch if needed, commit, push, open the PR, then review it.
- **Review-only mode**: an integer argument (e.g., `247`). Skip all git/commit/push/create steps and review the existing PR with that number.

If the argument is present but not an integer, error out: *"Usage: `/pr-audit` (auto mode) or `/pr-audit <number>` (review existing PR)."*

---

## Phase 1: Pre-flight checks

Run these in both modes.

1. Verify the current working directory is a git repository: `git rev-parse --git-dir`. If not, error out.
2. Verify `gh` CLI is installed and authenticated: `gh auth status`. If not, instruct the user to run `gh auth login`.
3. Check `.pr-audit/rules.md` in the repo root. If yes, read it and parse into domain sections (`## Security`, `## Correctness`, `## Performance`). Store each section for later subagent passing.

---

## Phase 2: Auto mode (skip in review-only mode)

### 2.1 Detect pending changes

Run `git status --porcelain`. Categorize:

- **No changes**: nothing to commit, no branch ahead of remote → error out: *"No pending changes to review. To review an existing PR, run `/pr-audit <pr-number>`."*
- **Uncommitted changes only**: continue to 2.2.
- **Committed changes ahead of remote**: skip to 2.4 (push directly).

### 2.2 Branch management

Get current branch: `git branch --show-current`.

- If on `main`, `master`, `develop`, `dev`, or `trunk` → MUST create a new feature branch. Generate a 3-5 word kebab-case name from the diff, prefixed with `fix/`, `feat/`, `refactor/`, or `chore/`. Run `git checkout -b <new-branch>`.
- Otherwise, stay on the current branch.

### 2.3 Commit pending changes

Generate a conventional commit message summarizing the diff:

```
<type>: <imperative summary>

<optional body>
```

Types: `fix`, `feat`, `refactor`, `chore`, `docs`, `test`, `perf`, `style`. Keep summary under 72 chars.

```bash
git add -A
git commit -m "<generated message>"
```

### 2.4 Push branch

```bash
git push -u origin HEAD
```

If push fails because remote does not exist, surface the error and stop.

### 2.5 Create or find PR

Check existing PR: `gh pr view --json number,url`. If exists, capture its number. Otherwise generate a title and description from `git log` of the branch's new commits.

PR description includes:
- One paragraph: what changed and why
- Bulleted list of significant file changes
- Note: *"Generated by pr-audit. Review comments will appear shortly."*

```bash
gh pr create --title "<title>" --body "<body>"
```

Capture the PR number from the output.

---

## Phase 3: Review-only mode entry

If invoked with `/pr-audit <number>`, skip Phase 2. Capture the PR number from the argument.

Run `gh pr view <number> --json number,url,headRefName,baseRefName,title,additions,deletions,changedFiles` to verify and capture metadata. If PR doesn't exist or is closed, error out.

---

## Phase 4: Fetch diff and apply noise filters

Both modes converge here.

1. Get the diff: `gh pr diff <number>`.
2. Apply noise filters per `references/noise-filters.md` — read that file with the Read tool and apply its patterns:
   - Match each diff file against path patterns. Drop matches.
   - For remaining files, read first 5 lines and check for generated-file markers. Drop except for `migrations/`, `drizzle/`, `prisma/migrations/` paths.
3. Compute the review scope (remaining files).
4. If scope is empty, post: *"This PR contains only auto-generated or non-code files. No code review performed."* Print a one-line handoff brief in the chat (verdict + PR link). Exit.

---

## Phase 5: Classify tier

Read `references/tier-decision.md` and `references/path-patterns.md`.

1. Compute `lines_changed` and `files_changed` across review scope.
2. Classify path flags: `security_sensitive`, `db_schema_changed`, `api_surface_changed`, `frontend_changed`, `doc_only_changes`.
3. Apply tier rules in order. Record the chosen tier and rationale.

Examples:
- 30 lines, 1 file in `src/utils/formatter.ts`, no special paths → **Inline**.
- 15 lines in `src/api/auth/login.ts` → **Standard** (security-sensitive override).
- 80 lines across components and utils → **Standard**.
- 250 lines including `prisma/schema.prisma` and a new API route → **Deep**.

---

## Phase 6a: Review (Inline tier)

If **Inline**, review the diff yourself without spawning subagents.

Read all three checklists:
- `references/security-checklist.md`
- `references/correctness-checklist.md`
- `references/performance-checklist.md`

Apply them in a single pass. Output a YAML structure following `references/output-schema.md`.

If `.pr-audit/rules.md` had matching sections, factor them in for each domain.

Proceed to Phase 7.

---

## Phase 6b: Review (Standard or Deep tier)

If **Standard** or **Deep**, spawn subagents in parallel via the Task tool. The agent definitions live in `${CLAUDE_PLUGIN_ROOT}/agents/`.

### Tier 1 — always spawned in Standard and Deep

- `security-reviewer`
- `correctness-reviewer`
- `performance-reviewer`

### Tier 2 — spawned in Deep tier only, conditionally

Based on path flags from Phase 5, also spawn:

- `architecture-reviewer` — if `db_schema_changed == true` OR if the diff modifies public exports (changes to `package.json` `exports`, `index.ts` re-exports, or removed/renamed exported symbols visible in the diff).
- `api-contract-reviewer` — if `api_surface_changed == true`.
- `a11y-reviewer` — if `frontend_changed == true`.
- `test-coverage-reviewer` — if any source file in the diff (non-test, non-doc, non-config) has no matching test sibling visible in the diff or in the context files. Test sibling patterns: `foo.ts` → `foo.test.ts`, `foo.spec.ts`, `__tests__/foo.test.ts`, or `tests/foo.test.ts`.
- `business-logic-reviewer` — if `.pr-audit/rules.md` exists in the repository root AND contains a section with heading `## Business Logic`. Read that section and pass it in this subagent's prompt.

A single Deep tier review may spawn between 3 and 8 subagents in parallel.

### Prepare the numbered diff

Subagents expect a hunk format with line numbers prefixed on each line (their
`# Diff format` section describes this). The raw `gh pr diff` output does not
have them. Before constructing any subagent prompt, convert the filtered diff
into this format:

- For each hunk, read the `@@ -old,+new @@` header to get the starting line
  number of the new file.
- Prefix every added (`+`) and context (` `) line with its line number in the
  new file. Removed (`-`) lines get no number.
- The result is what subagents call `__new hunk__`: each reviewable line carries
  its real line number, so findings anchor to exact lines with no guessing.

Pass this numbered diff — not the raw diff — to every subagent. The line numbers
a subagent puts in `start_line` / `end_line` must come directly from these
prefixes.

### Per-subagent prompt construction

For each subagent prompt, include:

1. The numbered diff (prepared above) — not the raw diff.
2. Context files: 0-3 files that may help. Selection heuristics:
   - **security-reviewer**: `src/middleware/auth.ts` and similar if present; `package.json` if new dependencies in diff.
   - **correctness-reviewer**: pre-change version of any heavily modified file.
   - **performance-reviewer**: `package.json` if dependency-related; otherwise no context files.
   - **architecture-reviewer**: pre-change version of `prisma/schema.prisma` or migration source files; `package.json`; `tsconfig.json`; barrel/index files if exports change.
   - **api-contract-reviewer**: route registry / router file (`src/routes.ts`, `app/router.ts` etc.); pre-change version of changed API files; `*.graphql` / `*.proto` files if changed.
   - **a11y-reviewer**: pre-change version of changed component files for diff context.
   - **test-coverage-reviewer**: any existing test files in the same directory as the changed source (orchestrator should glob and pass top 2-3 most relevant).
   - **business-logic-reviewer**: pre-change versions of files referenced in the rule text where useful.
   Use the Read tool to load file contents, include in the prompt with clear delimiters.
3. The relevant domain checklist from `references/`.
4. For domain-specific reviewers: matching section from `.pr-audit/rules.md` if present (e.g. pass `## Security` to security-reviewer, `## Performance` to performance-reviewer).
5. For business-logic-reviewer: the full text of the `## Business Logic` section.
6. The output schema (from `references/output-schema.md`).

Wait for all subagents to return. Each returns a YAML object with `findings: [...]`.

## Phase 7: Aggregate findings

### 7.1 Confidence filtering

Per `references/output-schema.md`:

- `confidence: high` → keep.
- `confidence: medium` → keep.
- `confidence: low` AND `severity: critical` → keep with explicit uncertainty note added to `issue_content`.
- `confidence: low` AND `severity != critical` → move to "Possibly worth checking" in handoff brief. Do NOT post on GitHub.

### 7.2 Deduplication

If two findings have the same file and overlapping line ranges with similar `issue_header`, merge into one. Prefer the higher severity. Concatenate `reasoning` if they add information.

### 7.3 Re-categorization

If a finding's `domain` does not match its content, move it to the correct domain.

### 7.4 Build the master findings table

Before computing the verdict, write out every surviving finding (post-filtering, post-dedup) into a single explicit table. Do not count from memory or eyeball the subagent YAML blocks — transcribe each finding into one row:

| # | Severity | Domain | File:line | Header |
|---|----------|--------|-----------|--------|
| 1 | critical | security | ... | ... |

Then derive the counts by tallying the `Severity` column of this table. This step exists because finding counts drive the verdict, and counting across many separate YAML blocks (3–8 subagents) by eye is error-prone — a miscount silently changes the verdict.

### 7.5 Compute verdict

Read `references/approval-rubric.md`. Count findings by severity (post-filtering, from the table in 7.4):

- `critical_count >= 1` → `significant_concerns`
- `critical_count == 0`, `warning_count >= 3` → `minor_issues`
- `critical_count == 0`, any other findings → `approved_with_comments`
- No findings → `approved`

The verdict itself is mode-independent — it is computed purely from finding counts. Only the **GitHub submit action** for that verdict depends on the mode (see Phase 8.4). A `significant_concerns` verdict in auto mode is still `significant_concerns`; it just posts as a `COMMENT` review instead of `REQUEST_CHANGES`.

### 7.6 Generate review summary

Write a 1-paragraph PR summary (max 150 words):
- What the diff changes (one sentence)
- Overall risk profile (one sentence)
- Top concerns if any (one sentence)
- Verdict statement (one sentence)

## Phase 8: Post to GitHub

### 8.1 Re-review awareness

Before posting, check existing PR comments for those authored by this plugin (HTML marker `<!-- pr-audit:finding:{id} -->`).

For each previous finding:
- If current findings include a matching one → keep open.
- If previous finding NOT in current findings → assume resolved. Reply `✅ Resolved in this revision.` and resolve thread via `gh api graphql`.

### 8.2 Post top-level summary

```bash
gh pr comment <number> --body "<summary with review details>"
```

Include in the summary body:
- The review_summary paragraph
- Tier classification + reason
- Subagents used
- Finding counts by severity
- Verdict
- Note that re-running `/pr-audit <number>` after fixes verifies them

### 8.3 Post inline comments

All inline comments are posted in **one batched review** via the GitHub API, not via the `gh pr review` CLI. The CLI does not support attaching multiple inline comments to a single review; attempting one `gh pr review` call per finding both fails the anchoring and trips GitHub's secondary rate limit.

Build a single JSON payload for `POST repos/{owner}/{repo}/pulls/{N}/reviews`:

```json
{
  "commit_id": "<HEAD SHA of the PR branch>",
  "event": "<see 8.4>",
  "body": "<short review body — the verdict statement>",
  "comments": [
    { "path": "<file>", "line": <start_line>, "side": "RIGHT", "body": "<comment body>" }
  ]
}
```

**Single-line vs multi-line anchoring.** The `comments` entry above shows a
single-line comment. The anchoring rule depends on whether the finding spans
multiple lines:

- **Multi-line finding** (`start_line` != `end_line`): the entry must also
  include `"start_line"` and `"start_side": "RIGHT"`, with `"line"` set to the
  END line of the range:

  ```json
  { "path": "<file>", "start_line": <start>, "line": <end>,
    "start_side": "RIGHT", "side": "RIGHT", "body": "<comment body>" }
  ```

- **Single-line finding** (`start_line` == `end_line`): send only `"line"`. Do
  NOT send `"start_line"`. GitHub rejects the whole review with HTTP 422 if
  `start_line` equals `line`.

Get the commit SHA with `git rev-parse HEAD` (auto mode) or from `gh pr view <N> --json headRefOid` (review-only mode). Post with:

```bash
gh api -X POST repos/{owner}/{repo}/pulls/{N}/reviews --input <payload-file>
```

Each comment `body`:

```
<!-- pr-audit:finding:{stable-id} -->
**{severity-emoji} [{severity}] {issue_header}**

{issue_content}

**Suggested fix:**

{suggested_fix}
```

Stable ID: hash of `file + start_line + issue_header`.

Severity emojis: 🔴 critical, 🟠 warning, 🟡 suggestion.

**Rendering the suggested fix.** For each finding, decide how to render `suggested_fix`:

- If the fix is a replacement of the exact contiguous line range the comment is anchored to (`start_line`–`end_line`), in a single file, render it as a GitHub suggestion block — fenced with ` ```suggestion ` — containing the corrected code for those lines. GitHub renders this with a one-click "Commit suggestion" button.
- Otherwise (multi-file fix, or the fix does not map to the anchored lines), render `suggested_fix` as a normal fenced code block plus the explanatory text.

Either way the fix and its code are always present in the comment; only the fencing differs.

If the API returns HTTP 403 with a **secondary rate limit** message, wait ~60–90 seconds and retry the same payload once. Do not split the review into per-comment calls — that makes the rate limit worse.

### 8.4 Apply verdict action

The GitHub action for the verdict depends on the **mode**, because GitHub rejects a formal `APPROVE` / `REQUEST_CHANGES` review on a PR authored by the same user (HTTP 422 "Can not request changes on your own pull request"). In **auto mode** the plugin created the PR, so it is always the author.

The batched review from 8.3 carries the verdict via its `event` field:

| Verdict | Auto mode `event` | Review-only mode `event` |
|---------|-------------------|--------------------------|
| `approved` | `APPROVE` | `APPROVE` |
| `approved_with_comments` | `COMMENT` | `APPROVE` |
| `minor_issues` | `COMMENT` | `COMMENT` |
| `significant_concerns` | `COMMENT` | `REQUEST_CHANGES` |

Notes:
- In **auto mode**, a formal `APPROVE` / `REQUEST_CHANGES` on your own PR is either disallowed or meaningless, so the review submits as `COMMENT`. The verdict is still stated explicitly in the review `body` and the top-level summary, so the outcome is unambiguous.
- In **review-only mode**, the PR is authored by someone else, so the formal `APPROVE` / `REQUEST_CHANGES` events apply and should be used.
- If a `submit` is still rejected by GitHub for an ownership reason, fall back to `COMMENT` for that review and note it in the summary. This is a safety net, not the primary path.

## Phase 9: Print handoff brief

Print a **short handoff brief directly in the chat / terminal**. Wrap the entire brief in a single fenced code block (```` ``` ````) so the user can select and copy it in one action — they may need to paste it into another session. Do NOT write a file — do not create `outputs/`, do not use the Write tool for the brief.

Use the exact structure, fields, and rules from `references/handoff-template.md` — that file is the single source of truth for the brief. Do not restate its contents here.

Rationale: every finding is already an inline comment on the GitHub PR. The brief is a quick orientation, nothing more — it never re-types finding details.

## Phase 10: Offer to apply fixes

After the handoff brief, ask the user — in this same session — whether they want the fixes applied now. Ask exactly one short line, do not expand it into a paragraph:

*"Want me to apply these {N} fixes now, or will you fix them elsewhere?"*

- **If the user will fix elsewhere** → stop here. Remind them in one line: copy the brief above, fix in another session or manually from the PR comments, then return here and run `/pr-audit {N}` again to verify (the re-review in Phase 8.1 marks resolved findings). Repeat until clean.
- **If the user wants the fixes applied now** → apply them in this session:
  1. For every finding, open the affected file and apply the fix.
  2. Detect the project's stack and its check commands from files in the repo root:
     - `package.json` → JS/TS. Read its `scripts`; run whichever check scripts exist (`typecheck`, `lint`, `test`). Fall back to `npx tsc --noEmit` only if a `tsconfig.json` is present.
     - `pyproject.toml` / `requirements.txt` / `setup.py` → Python. Run the linter/type-checker the project configures (`ruff`, `mypy`, `pyright`, `flake8`).
     - `go.mod` → Go. Run `go build ./...` and `go vet ./...`.
     - `Cargo.toml` → Rust. Run `cargo check` and `cargo clippy`.
     - If no recognized stack or no check commands exist, skip this step — do not invent commands.
  3. Run each detected check. If a check fails, it reports the exact file and line — fix that cause, then run the check again. Repeat until it passes. Never revert a finding's fix just to silence a check, and never move on to commit while a check is failing.
  4. Stage the changed files and create one commit: `fix: apply pr-audit findings`.
  5. Push to the PR branch.
  6. Tell the user what was done: which findings were fixed, that the checks passed, and that the commit is pushed to the PR branch.
  7. Ask — one short line — whether to run the verification now: *"Run `/pr-audit {N}` now to verify the fixes landed?"* If the user agrees, re-run `/pr-audit {N}` in this same session (the re-review in Phase 8.1 marks resolved findings; any finding still open re-enters Phase 10). If the user declines, stop.

## Constraints and invariants

- **Never push directly to `main` or `master`.** Always create a feature branch.
- **Never merge the PR.** The user merges manually.
- **No autofixing during the review.** Phases 1–9 only post findings — never patch code. Applying fixes happens only in Phase 10, and only after the user explicitly agrees.
- **Never read `CLAUDE.md`** and pass its content to subagents. `.pr-audit/rules.md` is the only authoritative config.
- **Subagents see only what their prompt includes.** No orchestrator state, no other subagents' findings, no unrelated repo files.
- **Inherit the user's model.** Use whatever Claude Code session is running.
- If any step fails, report clearly and stop. Do not silently continue with degraded behavior.
